# AGENTS.md

Developer and agent guide to the Log Cannon codebase. For product/usage docs see [`README.md`](README.md).

## What this is

A Seq-compatible log platform on Cloudflare. Log clients ship CLEF (or webhook/OTel) to one Cloudflare Worker, `workers/packages/ingest`, which authenticates the key against D1, parses the payload and writes the rows to Cloudflare Basin (the `log_events_v1` Pipelines stream into the Iceberg table `logs.events` on R2). The same Worker serves the read API (`/api/v1/query`, `/api/v1/logs`), the MCP server (`/api/mcp`), alerts and alert destinations (D1, evaluated on a once-a-minute cron), the Supabase platform-log pull, the replay of failed writes from an R2 spill bucket, and Basin retention.

The v1 stack (Cloudflare Queue → Go consumer → ClickHouse, read by a Next.js dashboard) was cut over on 2026-11-04 and stopped taking writes on 2026-11-10 (#163). The v1 ClickHouse stack was shut down and removed from the repo on 2026-11-22 (#171). Its history (everything before 2026-10-23 12:23 UTC, which Basin doesn't have) is kept as one final full ClickHouse backup in the `log-cannon-backups` R2 bucket under `final/`; the `MANIFEST.txt` beside it says how to restore it.

## Data flow

```
client ──CLEF/webhook/OTel──► Worker ── auth (D1) ── parse ──waitUntil──► LOGS stream ──► logs.events (Iceberg on R2)
                                                              └─ send failed ──► BASIN_SPILL (R2) ──► cron replay ──► LOGS
callers ──► /api/v1/query, /api/v1/logs, /api/mcp ──► Basin SQL (REST, read-only)
cron (every minute) ──► alerts (D1 + Basin SQL) · Supabase pull ──► LOGS · spill replay
cron (20:17 UTC)    ──► Basin retention (Iceberg delete snapshot; off in production)
```

## Build & run

- **Worker:** `cd workers && pnpm install`, then from `packages/ingest`: `pnpm exec tsc --noEmit -p tsconfig.json` (typecheck), `pnpm test` (vitest on workerd), `pnpm wrangler deploy --env production --dry-run` (config check). pnpm workspace, `packageManager` pinned in `workers/package.json`. The production deploy is Cloudflare Workers Builds on push to `main`.

## Conventions & gotchas

- **Basin is the only write, and it is off the response path (refs #169, #171).** Every ingest route and MCP `create_log` calls `copyToBasin` (`src/index.ts`), which registers the write in `waitUntil` synchronously and yields a macrotask before parsing, so the client's response never waits for the parse or the send. It must be called with nothing awaited between it and the response: a client that disconnects ends the invocation at the next `await`, and a copy registered after one is lost without a trace (#175). The write needs `BASIN_WRITE = "true"` and the `LOGS` binding; without both, ingest answers 2xx and stores nothing. Large CLEF and OTLP bodies are split into ≤90 KB chunks (`MAX_CHUNK_BYTES`, inherited from the queue's message cap) and parsed one chunk at a time, which bounds the copy's memory on a 32 MB body; a single line or resource entry over that is a 413. The Cloudflare Queue, its producer binding and the Go consumer are gone; don't reintroduce a second write path without discussion.
- **`logs.events` is at-least-once, not exactly-once.** A retried send, a send that timed out but landed, and a spill replay can all store a row twice. Rows keep their `id`, so a duplicate shows as `count(*) > count(DISTINCT id)`. Anything built on `count(*)`, alert conditions included, should tolerate a small over-count.
- **The v2 read API's canonical paths are the unprefixed v1 ones (refs #168).** The ingest Worker serves `/api/v1/query`, `/api/v1/logs`, `/api/mcp`, `/api/v1/alerts*` and `/api/v1/alert-destinations` (`readPath()` in `src/index.ts`), with `/v2/...` kept as an alias for callers that moved early. Unprefixed `/api/v1/logs` rows carry `timestamp` beside `ts`, because v1 callers read `row.timestamp`; `/v2` doesn't add it. The five production routes went live at the 2026-11-04 cutover (`3a5b37f`).
- **v2 alerts run on the ingest Worker's cron, `live` in production since 2026-11-04 (refs #165).** `src/alerts/` holds alerts and destinations in D1 (`migrations/0002_alerts.sql`) and evaluates the due ones once a minute against Basin SQL. `ALERTS_MODE` is `off` (default), `shadow` (evaluate and record in `alert_evaluations`, on a separate cooldown column, send nothing) or `live` (deliver, cooldown only on an accepted delivery). Every `now()` in an alert query is pinned `ALERT_LAG_SECONDS` (180) back, because Basin trails ingest by 1–2 minutes and a window ending at the true now would make every zero-count alert fire on data that hasn't landed. `ALERT_BATCH_MODE` (refs #194; `off`, `shadow` default, `on`) folds a tick's due alerts into one Basin query per 10 (`src/alerts/batch.ts`: each alert's SQL becomes a CROSS JOINed derived table, columns read from its top-level `AS` names and mapped back), because every query bills at least 10 MB; the freshness check rides in the first batch, an alert whose columns can't be read or whose last run was a query error runs alone, and a failed batch (Basin's count(DISTINCT) "scan budget exceeded" refuses ~200 MB batches) falls back to one query per alert. In `shadow` the per-alert results fire and each mismatch is an `Alert batch shadow mismatch …` Warning plus a per-tick `Alert batches …` summary. The condition grammar is a port of the retired Go `alert-worker`'s, quirks included (`&&` splits before `||`). `scripts/seed-cooldowns.py` copied v1's `last_triggered_at` into D1 at the cutover (refs #170). Email needs `SAASMAIL_API_URL` and `ALERT_FROM_EMAIL` (declared in `[env.production.vars]`) plus the `SAASMAIL_API_KEY` secret, and `POST /api/v1/alerts/:id/test` with `"deliver": true` sends through an alert's real destinations without starting its cooldown. A webhook destination's `config.headers` (the v1 import carried a secret token header across) are sent on every request, overriding `Content-Type` as v1 does; they sit in D1 in plain text like the rest of the config, and `GET /api/v1/alert-destinations` (v1 and v2) shows their values only to a `write` key; a `read` key gets the names with `********` values (refs #178). The Worker's own telemetry (`sendTelemetry`) goes to Basin, so readers and alerts see `log-cannon-ingest` and `log-cannon-alerts` events. Firing history (refs #193) is D1 `alert_firings` (`migrations/0004_alert_firings.sql`): one row per live evaluation whose condition was true (`delivered`, `cooldown` or `failed`), none in shadow, written as one batch per tick after every delivery so a failed insert is reported (`Alert firing history not recorded …` on the alerts source) and never holds a send; the minute-0 tick prunes rows past 90 days, at most 10,000 per run. MCP `list_alerts`, `get_alert_history`, `update_alert` and `test_alert` call the REST handlers with the key's own `ApiContext`, so their scope checks are REST's.
- **v2 pulls Supabase platform logs on the ingest Worker's cron, on in production (refs #164).** `src/supabase/` is the port of the retired Go `supabase-pull`: for each `ref=source` in `SUPABASE_PULL_PROJECTS` (in production a var set on the deployed Worker, not in `wrangler.toml`, because it names projects and the repo is public; `keep_vars = true` preserves it across deploys. Empty is a no-op; it also needs `BASIN_WRITE` on and the `SUPABASE_ACCESS_TOKEN` secret) it pages the Management API logs endpoint per table and sends the rows to `LOGS` as `format = 'supabase'`, `key_id = 'supabase-pull'`, Basin `id` = `sb_id`, with the same `Source`/`LogTable`/`ProjectRef`/`sb_*` properties the Go service wrote; alerts filter on those names, so renaming any of them breaks them silently. State is in D1 (`migrations/0003_supabase_pull.sql`), never read back from Basin: `supabase_pull_cursor` holds each table's newest sent row and `read_to`, `supabase_pull_seen` the ids sent inside the 5-minute overlap (pruned to the overlap behind each table's position), and the `supabase-pull` row in `cron_leases` keeps runs from overlapping. The cursor moves only after Basin accepted the page, so delivery is at-least-once and a duplicate shows as `count(*) > count(DISTINCT id)`. Per tick: at most 10 pages per table, a 429 ends that table without moving its cursor (reported as `RateLimited`, not a failure), and a 5xx or "Backend error" gets one 2 s retry. `function_edge_logs` rows drop `sb_request_cf_*`, most request/response headers, deployment and JWT bookkeeping and every IP-shaped key, which takes them from ~2.6 KB to ~0.9 KB, under Basin's 2,000-byte `json_get` limit; other tables are untouched. The per-run summary goes to source `supabase-pull` through `sendTelemetry` with the Go templates and properties, plus `Puller: "worker"`; its `Tables` lists only failed, rate-limited or behind tables. Don't point another shipper at an enabled project: every event would arrive twice, and the endpoint allows 10 requests per window per project.
- **A Basin write that fails is retried, then spilled to R2 and replayed (refs #166).** `writeCopy` (`src/basin.ts`) retries a failed `LOGS` send from one budget per copy (0.5 s, 2 s, 5 s; no retry starts past 12 s), and cuts each attempt at 5 s, so the copy, spill included, ends inside `waitUntil`'s ~30 s: the spill put gets 7 s (`SPILL_TIMEOUT_MS`), then, if it failed or stalled, one more put under a new key in the time left before the watchdog less 2 s (`SPILL_RESERVE_MS`; `SpillAttempts: 2` on the event, refs #190), and a copy still running at 28 s (`COPY_WATCHDOG_MS`) is reported lost. When the retries run out nothing more is sent: the failing batch, the batches behind it and the bodies not yet parsed go, as parsed rows with their `id`, to one gzipped NDJSON object per copy in the `BASIN_SPILL` bucket (`log-cannon-basin-spill` in production; absent, the rows are lost and reported), keyed `spill/<received_at>/<uuid>.ndjson.gz` so a list is oldest first. A row is sent or spilled, never both. The `basin-copy-failed` event carries `SpilledRows`/`LostRows`/`SpillError` and is a Warning when every unsent row was spilled, an Error when any was lost; losses throttle on their own channel. `sendTelemetry`'s Basin copy retries and spills the same way, with a 3 s spill limit (`TELEMETRY_SPILL_TIMEOUT_MS`), because a loss report starts only after the copy it describes has failed. The cron's `basinSpillReplayTick` (`src/basin-spill.ts`, lease `basin-spill-replay`, 45 s deadline, at most 200 objects) sends objects oldest first and deletes each only after every row went out; a failed send ends the tick with no retry, and a part-sent object is rewritten as its unsent remainder. A tick that did work or saw a backlog emits one `Basin spill replay sent …` summary (`Replayed`, `Objects`, `Backlog`, `OldestAgeSeconds`; Warning past 30 minutes) to `SLOW_REQUEST_SOURCE`. An object that can't be read back stays, counted as `Unreadable`, until someone removes it. Replay is at-least-once like the rest: a send that failed after Basin took it duplicates, visible as `count(*) > count(DISTINCT id)`. The Supabase pull doesn't spill: its cursor holds on a failed send.
- **Basin SQL misses rows on `=`, `IN`, prefix `LIKE` and range filters over `message`, `message_template`, `properties` and `exception` (refs #187).** Basin's writers (Pipelines and managed compaction) record a string column's manifest upper bound from one row group instead of the whole file, and the reader prunes on it. Write those filters as `LIKE '%…%'`, which can't prune. Treat `id` the same way: `/api/v1/events/{id}` matches it with `strpos` and `octet_length` inside a time window, and search cursors only compare `id` under `ts = <cursor ts>` (refs #191). `workers/packages/ingest/basin/check-manifest-bounds.py` finds bad files from their Parquet footers, and `repair-manifest-bounds.py` rebuilds their manifest entries; an hourly job on the agent host runs both, so data older than about an hour is right. Basin's catalog rejects `write.metadata.metrics.*`, so the bounds can't be switched off.
- **v2 retention drops whole day partitions on its own daily cron, and is off in production (refs #167).** Basin SQL is read-only and `logs.events` is partitioned by `day(__ingest_ts)` only, so `src/basin-retention.ts` can't delete per key. Instead, once a day (`RETENTION_CRON`, 20:17 UTC; `scheduled` routes that cron here and every other tick to the minute jobs; lease `basin-retention`, 15 min), it commits one Iceberg `delete` snapshot through the REST catalog. That snapshot drops every data file whose ingest day ended before `now − longest window`. It is metadata only: the affected manifests are rewritten (`src/avro.ts`; reads `null` and `deflate`, writes `null`) with those files marked DELETED and the rest carried as EXISTING, a new manifest list is written, and `main` is swapped under `assert-ref-snapshot-id`. A 409 from a Pipelines append or compaction landing first reloads and retries, up to 4 attempts, after removing the losing attempt's files. The catalog's own snapshot expiration (7 days, keep 5, hourly) then deletes the files from R2. Windows come from D1 `api_keys.retention_days`; `0` (v1's "forever") and key_ids not in D1 get `BASIN_RETENTION_DEFAULT_DAYS` (30). The longest of all of them sets the cutoff, so a 21-day key keeps up to the longest window plus a day. `BASIN_RETENTION_MODE` is `off` (default, and production since 2026-11-10), `dry-run` (plan, report, change nothing) or `delete`, which also needs the `BASIN_CATALOG_TOKEN` secret (R2 Data Catalog write) and the `BASIN_EVENTS` binding to the catalog bucket. Delete mode without the token plans like a dry run and reports the error. Each run emits one `Basin retention …` summary on `log-cannon-ingest` (`Mode`, `Cutoff`, `Partitions`, `Files`, `Records`, `OldestIngest`, `OldestIngestAgeDays`, `KeysPastOwnWindow`, `Overdue`). It is a Warning when the run failed or the oldest row's **ingest** time is more than the longest window + 2 days old. It is never an Error, because `level = 'Error'` on this source is what the loss alert pages on. Ages are judged on `__ingest_ts`, never `ts`, because senders backdate `ts`.
- **API keys live in D1, behind the ingest Worker.** The Worker owns the only write path (`/v1/keys`, admin scope); nothing else writes keys. Never add a second key store — that dual-homing was the bug this replaced. See `docs/superpowers/specs/2026-08-06-api-key-registry-d1-design.md`.
- **Worker rollback caveat.** Rolling the Worker back to a pre-D1 (KV) commit leaves D1 intact, but that old build reads KV — which is no longer bound or written. A key disabled or deleted **stays valid at the edge indefinitely** in that state, not for the ~5 minute auth-cache window that normally bounds staleness. Don't roll back past the D1 cutover; if you must, re-bind the old `API_KEYS` KV namespace and mirror pending revocations into it by hand until the Worker is rolled forward again.
- **Config via env only.** No secrets in the repo. The Worker's secrets are Worker secrets (`wrangler secret put`); its non-secret config is `[vars]` in `wrangler.toml`.
- **CLEF is the contract.** Seq/Serilog compatibility is a core feature — preserve the `/ingest/clef` and `/api/events/raw` endpoint shapes and CLEF field semantics.
- **The ingest Worker instruments itself, and must not forward its own logs.** `[observability]` is on (invocation logs, `head_sampling_rate = 1`), `src/timing.ts` owns what a slow request is and how it renders, and the router's `reportIfSlow` sends it two ways: a `console.warn` retained by Workers Logs, and a CLEF `Warning` written to Basin on `SLOW_REQUEST_SOURCE` in `waitUntil`. Do **not** add `observability.logs.destinations` here — that shape is correct for every other Worker, but on this one the destination delivers to `/ingest/webhook` on the Worker whose invocations it is reporting, and each delivery generates more. The stored event is throttled per isolate on purpose: the wrong answer to a struggling store is more writes. Its `EnqueueMs` and `QueueMessages` are always 0 since the queue was retired, and stay so the event's `@mt` (and so its `event_type`) doesn't change. Timing spans measure I/O only (Cloudflare freezes `Date.now()` between I/O) and start at invocation, so cold start and connection setup are outside them.
